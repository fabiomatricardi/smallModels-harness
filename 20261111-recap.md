## 1. The question

Andrej Karpathy (a well-known AI researcher) argued that most of a big language model's size is used to **memorise facts**, and that the actual *thinking* part — he calls it the "cognitive core" — might fit in about **1 billion parameters**.

A **parameter** is one of the adjustable numbers inside a neural network. Big models have hundreds of billions; small ones have one or two billion. More parameters generally means more knowledge and more capability, but also more cost.

His claim, in plain words: *a small model with good tools should be able to do real work, because the tools and the feedback loop matter more than raw size.*

We tested that on a laptop.

---

## 2. The setup, in beginner terms

| Term | What it means here |
|---|---|
| **Model** | `LFM-3-Coder-Claude-Distill`, **1.73 billion parameters** — a small open model made by a hobbyist ("Schnuckade") by fine-tuning Liquid AI's LFM3-1.7B |
| **GGUF / Q5_K_M** | A file format for running models on ordinary computers. "Q5" means the numbers were **compressed to about 5 bits each** — smaller and faster, slightly less accurate |
| **llama.cpp** | The free program that runs the model |
| **Vulkan** | The graphics technology used to make the laptop's graphics chip do the maths |
| **iGPU** | A graphics chip built into the processor, sharing the laptop's 31.5 GB of memory — not a dedicated graphics card |
| **Token** | A chunk of text, roughly ¾ of a word. **20.8 tokens/second** is the reading-out speed |
| **Context window (16,384 tokens)** | How much text the model can keep "in view" at once |
| **Tool call** | The model asks the surrounding program to run a function, e.g. *look up record r5*, and gets the result back |
| **Harness** | The surrounding program that supplies tools, executes them, feeds results back, and decides when to stop |
| **Agent** | Model + harness + a loop of "think → call tool → read result → repeat" |

The **benchmark** was 30 tasks I wrote, in six difficulty levels ("tiers"):

- **A0** — no tools, just read a short paragraph and answer
- **A** — one tool call
- **B** — two calls, the second uses the first's result
- **C** — branch: check a value, then choose one of two actions
- **D** — combine several sources that disagree
- **E** — long task, 8–12 calls, with rules that must be respected throughout

Each task has a known correct answer. A run passes only if the answer is exactly right **and** the required tool calls happened.

**Five harness versions** ("arms") were compared, all on the same model and tasks:

| Arm | What changes |
|---|---|
| `json` | Tools described in text; model writes JSON by hand |
| `native` | Model uses its built-in tool-call format |
| `verifier` | Same, but a rejected answer is sent back with the error, up to 3 tries |
| `nudged` | Same, plus "you MUST submit an answer" in the instructions |
| `deadline` | Warns the model when 2 calls remain, and forces a final answer on the last call |

## 3. How to read the scores

Two different questions, two different metrics:

- **pass@1** — "If I run it once, how often is it right?" This is an *accuracy* number.
- **pass^k (all)** — "If I run it k times, how often is it right **every single time**?" This is a *reliability* number, and it is what you care about in production.

**Temperature** is a randomness dial: 0 means the model always gives the same answer; 0.7 means it varies. At temperature 0, running five times gives five identical results, so "reliability" would be fake. That is why the reliability experiment used **temperature 0.7, five runs per task, with a fixed random seed**.

**95% CI** (confidence interval) is an uncertainty range. "70%, CI 62–77" means: our best estimate is 70%, and if we repeated the whole experiment, the true value would plausibly fall between 62% and 77%. It stops us pretending a small sample is exact.

## 4. The results

### Experiment 1 — does the tool interface matter? (180 runs)

| Arm | Overall success |
|---|---|
| JSON written by the model | **47%** |
| Native tool calls | **73%** |

Same model, same tasks, same laptop. Changing only *how tools are presented* moved success by **26 percentage points** (not 26% — it is the gap between 73 and 47).

This is the strongest result in favour of Karpathy: the surrounding system mattered more than the model.

### Experiment 2 — reliability (300 runs, 5 attempts each)

| Arm | pass@1 | pass^5 (all 5 correct) |
|---|---|---|
| Native tools | 70% (CI 62–77) | **57%** |
| With deadline policy | **76%** (CI 69–82) | **67%** |

By difficulty:

| Tier | Native, all-5 correct | With deadline |
|---|---|---|
| A0 (no tools) | 40% | 40% |
| A (one call) | 100% | 100% |
| B (two calls) | 100% | 100% |
| C (branch) | 60% | **100%** |
| D (combine sources) | 20% | **60%** |
| E (long task) | 20% | **0%** |

Read that bottom row carefully: on the hardest tasks, the best harness got **zero** tasks right five times out of five.

### Experiment 3 — smaller interventions

- **Deadline policy**: "never submitted an answer" failures went from **27 to 0**. But wrong submissions rose from **5 to 24**. It did not make the model smarter; it made it commit.
- **Verifier (feedback)**: fixed one task completely, broke another, net zero. It helps when the error is a wrong number; it cannot help when the model picked the wrong source.
- **Reasoning mode** ("thinking", with a 512-token cap): on six sampled tasks, 5/6 became **6/6**. It fixed the counting task and, on one task, used fewer tool calls (6 instead of 10).
- **Configuration change**: using one server slot and a 16,384-token window instead of four slots × 2,048 changed the score by **nothing** (73% both times) — but the largest prompt was **2,207 tokens**, so the old setup had a silent truncation risk.

### The most embarrassing number

On **A0-1**, the model is given six short sentences saying which projects are active, and asked how many are active. The answer is 3. With thinking off, it answered **4**, every time. Even across five attempts with thinking available, it was right in all five only **40% of the time**.

There is no outside knowledge involved. Just counting. That is the clearest evidence that a 1.7B "reasoning core" is not reliable.

## 5. What the article draft reports

**Title:** *How to Get Reliable Agent Work Out of a 1.7B Model (and Where It Still Fails)*
**Angle:** "Karpathy is right about the system, wrong about the core." It is deliberately **contrarian but fair** — it concedes the +26-point harness result before criticising the 1B claim.
**Length:** ~2,650 words, first person, English.

It reports, in order:

1. The setup and the exact `llama-server` flags (including the `-np 1` trap that halves your usable context).
2. The 47% → 73% interface result.
3. Why pass^k — not pass@1 — is the honest metric, with the tier table.
4. The deadline experiment: 27 → 0 stalls, 5 → 24 wrong answers.
5. The verifier: fixes numbers, never judgment.
6. Thinking mode and the counting failure.
7. Cost: **~$0.003 per passed task**, 20.8 tokens/second.
8. A routing table: which work to give the small model, which to keep on a bigger one.
9. What would change the author's mind.

It also discloses the limitations **in the article itself**: one model, a hobbyist fine-tune, 30 self-written tasks, one laptop, five attempts, no comparison against the official base model.

## 6. What is *not* proven

Be careful with these — they are the honest weak points:

- **It is one model**, and not even the official one: a community fine-tune, not Liquid AI's original.
- **The tasks are mine.** 30 tasks, 5 per level. A probe, not a leaderboard. Someone else's tasks could score differently.
- **No control run** against `LiquidAI/LFM3-1.7B` (the base model). This is the biggest gap.
- **Five attempts is a small sample.** The confidence intervals are wide.
- **Grading is exact-match**, and the A0 questions use substring matching, which is permissive.
- **Vendor numbers were not reproduced.** The model card's impressive figures are the vendor's own, from their own setup.

So the safe conclusions are: *the interface mattered a lot; short tasks worked; long tasks did not; feedback fixed numbers but not judgment.* The specific percentages should be treated as approximate.
